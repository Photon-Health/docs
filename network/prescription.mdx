```graphql
prescription(prescription: PrescriptionInput!, metadata: RequestMetadata!): PrescriptionResult!
```

| Call | `prescription` input | Result |
| --- | --- | --- |
| **Get** | `{ id }` | The prescription, draft or signed. Nothing changes. |
| **Sync**, no patient | `{ treatment }` | A drug lookup: the matches come back as options. **Nothing is created.** |
| **Sync** | `{ patient, templateId }` or `{ patient, treatment, … }` | A new draft, or the patient's draft in progress continued |
| **Update** | `{ id, …fields }` | That draft, with only those fields changed |
| **Sign** | `{ id, signing: { signedHash } }` | The prescription, signed. Needs `write:prescription`, which only a prescriber's [user token](/authentication#permissions) has. Drafting doesn't. |

Every call screens the draft and returns its `screeningAlerts`. See [Screening](/network/screening).

## Example

<CodeGroup>

```graphql Mutation
mutation Prescription($prescription: PrescriptionInput!, $metadata: RequestMetadata!) {
  prescription(prescription: $prescription, metadata: $metadata) {
    __typename
    ... on PrescriptionPayload {
      prescription {
        id
        treatment { id name }
        instructions
        dispense { quantity unit daysSupply refillsAllowed }
        screeningAlerts { severity type description }
        signing { state contentHash }
      }
      changes { key status severity reason options { displayName argument value } }
    }
    ... on AmbiguousPrescriptionMatch { reason candidates { id instructions } }
    ... on OperationError { type code message }
  }
}
```

## Choosing the drug

Identify the treatment by exactly one of `id`, `rxNormId`, `ndc`, `upc` or `name`, or start from a `templateId`, which fills in the drug, sig and dispense. An `id` resolves exactly. A name that fits several products comes back as an `AMBIGUOUS` change whose options are the candidate drugs. So does a name that fits one product without being its exact name, with that one option to confirm (`CONFIRMATION_REQUIRED`). Resend with the chosen option's `value` (a `treatment.id`). See [Changes and choices](/network/changes).

Syncing without a patient is a safe lookup that never creates anything. Use it to resolve the drug before you draft.

Each drug option's `entity` is the `Treatment` it picks, in parts. Use them to show the choices as a prescriber decides (drug, then form, then strength) instead of parsing `displayName`:

```graphql
changes {
  key
  status
  options {
    displayName
    value
    entity {
      ... on Treatment { brandName genericName form route strength schedule medicationType recommendedDispenseUnits }
    }
  }
}
```

| Field | Example | Notes |
| --- | --- | --- |
| `brandName` | `"Lipitor"`, `"Zepbound KwikPen"`, `"Lisinopril"` | The product's name: a brand, or for a generic, the drug |
| `genericName` | `"Atorvastatin Calcium"` | Its ingredients |
| `form` | `"Tablet"`, `"Solution Auto-injector"` |  |
| `route` | `"Oral"`, `"Subcutaneous"` |  |
| `strength` | `"10 MG"`, `"125 MG/5ML"` |  |
| `schedule` | `"II"`, `"UNCONTROLLED"` | DEA schedule. On a lookup's options only. |
| `medicationType` | `"RX"`, `"OTC"` |  |
| `recommendedDispenseUnits` | `["Bottle", "Tablet"]` | Values for `dispense.unit`. On a lookup's options only. |

These are null for medical equipment and compounds. A prescription's own `treatment` has the same parts. Its `name` may be just the drug (`"Lisinopril"`), and `prescribableName` is the full product name.

<Warning>
  Always send a `templateId` or a `treatment` when you draft. With a patient, a sync may continue a draft the patient already has in progress. If they have several, you get `AmbiguousPrescriptionMatch`. Resend with the `id` of the one you mean.
</Warning>

## Sig options

Once a draft has a patient and a drug with an NDC, `structuredSigs` suggests sigs for that drug and patient, worded for the patient:

```graphql
structuredSigs {
  sigs { instructions }
  notices { kind message }
}
```

```json
{
  "sigs": [{ "instructions": "Take 1 tablet (25 mg) by mouth 2 times per day with food" }],
  "notices": []
}
```

To use one, send its `instructions` as the prescription's `instructions`. Each sig also has a `dispense`, but its fields are all null for now, so the prescriber still enters the quantity, unit and days supply.

`structuredSigs` is null until the draft has both a patient and a drug with an NDC, and on a signed prescription. When no sig fits, `sigs` is empty and `notices` says why:

| `kind` | Means |
| --- | --- |
| `MISSING_INPUT` | A patient detail needed to find sigs is missing, such as kidney function |
| `NO_MATCH` | No sig fits this patient, such as an age the drug isn't dosed for |
| `CONTRAINDICATED` | The drug is contraindicated for this patient |
| `NOT_APPLICABLE` | Sigs don't apply to this product, such as test strips |
| `DEFAULT_VALUE_USED` | A typical weight or body surface area for the patient's age and sex stood in for one Photon doesn't have |
| `OTHER` | Any other message, including a lookup that couldn't be done |

Looking sigs up takes longer than the rest of a prescription, so select `structuredSigs` only when you'll show it, such as in a separate get.

## Signing

Signing is the prescriber's approval of exactly what they reviewed:

1. Every response includes `signing.contentHash`, a hash of the prescription's current clinical content: the drug, the sig and the dispense. Notes and diagnoses aren't part of it, so changing them doesn't invalidate a signature.
2. Show the prescriber the prescription and its screening alerts.
3. Send that hash back as `signing.signedHash`, and send no other changes in the same call.

If the content changed after the prescriber reviewed it, the hashes don't match. Photon rejects the attempt and returns `INVALIDATED_SIGN`. Show the prescriber the new content and sign again.

| `signing.state` | Meaning |
| --- | --- |
| `UNSIGNED` | Not signed yet |
| `SIGNED` | Signed. The prescription is final, and a change means writing a new one. |
| `INVALIDATED_SIGN` | The hash sent doesn't match the current content |

<Note>
  Only a prescriber's [user token](/authentication) can sign. A machine token gets an `OperationError` with `type: UNAUTHORIZED`. Most integrations let [Prescribe](/prescribe/overview) do the signing.
</Note>

## Fields

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `ID` | Leave it out to draft a new prescription |
| `externalId` | `String` | Your own id for the prescription, scoped to your organization. An [order](/network/order#fields) can add the prescription by it. |
| `patient` | `PatientReferenceInput` | Usually `{ id }`. Without it, a sync only looks the drug up. |
| `templateId` | `ID` | Fills in the drug, sig and dispense. Find ids under [Settings → Templates](https://app.neutron.health/settings/templates). |
| `treatment` | `TreatmentReferenceInput` | Exactly one of `id`, `rxNormId`, `name`, `ndc` or `upc` |
| `instructions` | `String` | The sig |
| `dispense` | `{ quantity, unit, daysSupply, refillsAllowed, dispenseAsWritten }` | |
| `clinical` | `{ diagnoses, notes }` | `diagnoses` is a patch of the ICD-10 codes that justify this prescription |
| `signing` | `{ signedHash, message }` | See [Signing](#signing) |

A prescription's `prescriber` is the prescriber assigned to it (`usr_…`), with their `name`. It's null for drafts and when no prescriber is assigned, and it doesn't say who signed. `signing` does.
